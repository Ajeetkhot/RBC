# Corporate Banking API Specification

## Base URL

http://localhost:8000/api

---

## Account APIs

### 0. Create Account For Maker

POST /api/accounts

Use the maker's ID in `userId` to assign the account to that maker. The account must have `availableBalance` less than or equal to `balance`.

Request body:

```json
{
  "accountNumber": "10000022334",
  "accountType": "CURRENT",
  "currency": "INR",
  "balance": 100000.00,
  "availableBalance": 100000.00,
  "userId": 2
}
```

Example response:

```json
{
  "id": 2,
  "accountNumber": "10000022334",
  "accountType": "CURRENT",
  "currency": "INR",
  "balance": 100000.00,
  "availableBalance": 100000.00,
  "status": "ACTIVE"
}
```

### 1. Get Account List

After creating an account, first call `GET /api/accounts/user/2` and use the `id` returned in that response as `debitAccountId`. Account IDs are generated by the database, so `debitAccountId: 2` is only valid if the response actually contains an account with ID `2`.

GET /api/accounts/user/{userId}

Example:

GET /api/accounts/user/1

Example response:

```json
[
  {
    "id": 1,
    "accountNumber": "10000012345",
    "accountType": "CURRENT",
    "currency": "INR",
    "balance": 100000.00,
    "availableBalance": 95000.00,
    "status": "ACTIVE"
  }
]
```

### 2. Get Account Details

GET /api/accounts/{accountId}

Example:

GET /api/accounts/1

## RBC Dependency APIs

The Maker-Checker application loads the reusable `com.example:rbc:1.0.0` JAR. These endpoints are available from the same application on port `8000`.

### Check authorization

POST `/rbc/check`

```json
{
  "applicationKey": "MAKER_CHECKER",
  "userId": 1,
  "action": "INITIATE_TRANSFER",
  "resource": "BANKING_RESOURCE",
  "context": { "amount": 4000 }
}
```

Expected response: `allowed: true` for 4000 and `allowed: false` for 7000.

### Create Maker and Checker roles

POST `/rbc/roles`

```json
{
  "applicationKey": "MAKER_CHECKER",
  "name": "MAKER",
  "active": true
}
```

Create the Checker role with the same API:

```http
POST http://localhost:8000/rbc/roles
Content-Type: application/json
```

```json
{
  "applicationKey": "MAKER_CHECKER",
  "name": "CHECKER",
  "active": true
}
```

GET `/rbc/roles/MAKER_CHECKER`

### Create a Maker user

```http
POST http://localhost:8000/rbc/users
Content-Type: application/json
```

```json
{
  "applicationKey": "MAKER_CHECKER",
  "userId": 2,
  "displayName": "Maker Two"
}
```

Assign the `MAKER` role to that user:

```http
POST http://localhost:8000/rbc/users/2/roles
Content-Type: application/json
```

```json
{
  "applicationKey": "MAKER_CHECKER",
  "roleName": "MAKER"
}
```

### Create a Checker user

```http
POST http://localhost:8000/rbc/users
Content-Type: application/json
```

```json
{
  "applicationKey": "MAKER_CHECKER",
  "userId": 201,
  "displayName": "Checker One"
}
```

Assign the `CHECKER` role to that user:

```http
POST http://localhost:8000/rbc/users/201/roles
Content-Type: application/json
```

```json
{
  "applicationKey": "MAKER_CHECKER",
  "roleName": "CHECKER"
}
```

The same APIs can create additional users, for example makers `1`, `2`, `3` and checkers `201`, `202`, `203`. The user IDs must match the IDs used by the Maker-Checker request payloads. These APIs configure authorization data only; they do not provide login or authentication.

### Configure a permission rule

POST `/rbc/rules`

```json
{
  "applicationKey": "MAKER_CHECKER",
  "roleName": "MAKER",
  "action": "INITIATE_TRANSFER",
  "resource": "BANKING_RESOURCE",
  "effect": "ALLOW",
  "active": true,
  "conditionsJson": "[{\"field\":\"amount\",\"operator\":\"LESS_THAN_OR_EQUAL\",\"value\":5000}]"
}
```

GET `/rbc/actions/MAKER_CHECKER`

GET `/rbc/resources/MAKER_CHECKER`

PUT `/rbc/rules/{ruleId}` enables, disables, or changes a permission:

```json
{
  "effect": "ALLOW",
  "active": false,
  "conditionsJson": "[]"
}
```

### Built-in Maker-Checker demo checks

The first application startup seeds rules for maker IDs `1`, `2`, `3` and checker IDs `201`, `202`, `203`:

- Maker `1`: initiate transfers up to 5000.
- Maker `2`: create beneficiaries and initiate transfers up to 10000.
- Maker `3`: initiate transfers up to 2000.
- Checker `201`: approve only transfers created by maker `1`.
- Checker `202`: approve transfers up to 10000.
- Checker `203`: approve transfers created by maker `1` or `2`.

The business APIs remain under `/api`:

```text
POST /api/beneficiaries
POST /api/transfers
GET  /api/checkers/201/pending
POST /api/checkers/201/approve/{transactionId}
POST /api/checkers/201/reject/{transactionId}
```

Authorization failures return HTTP 400 and are recorded as `ACCESS_DENIED` audit events.

## Audit Dependency APIs

The application loads the reusable `com.example:audit-trail:1.0.0` JAR. Audit events are stored in the `audit_events` table.

### Record a generic event

POST `/audit/events`

```json
{
  "applicationKey": "MAKER_CHECKER",
  "eventType": "ACCESS_DENIED",
  "actorId": 1,
  "resourceType": "BANKING_RESOURCE",
  "resourceId": "TRANSFER_REQUEST",
  "action": "INITIATE_TRANSFER",
  "description": "Amount exceeded configured permission",
  "metadata": { "amount": 7000 }
}
```

### Query audit history

```text
GET /audit/events
GET /audit/events/application/MAKER_CHECKER
GET /audit/events/actor/1
GET /audit/events/resource/FUND_TRANSFER/TXN100001
```

Maker-Checker records `ACCESS_ALLOWED`, `ACCESS_DENIED`, `BENEFICIARY_CREATED`, `TRANSFER_INITIATED`, `TRANSFER_APPROVED`, and `TRANSFER_REJECTED`.

## Assessment Coverage

- Admin role configuration: supported by `/rbc/roles`.
- User and role assignment: supported by `/rbc/users` and `/rbc/users/{userId}/roles`.
- Resource and action configuration: derived from persisted rules through `/rbc/resources/{applicationKey}` and `/rbc/actions/{applicationKey}`.
- Conditional permissions: supported by rule conditions and the `EQUALS`, `NOT_EQUALS`, comparison, and `IN` operators.
- Enable/disable permissions: supported by `PUT /rbc/rules/{ruleId}` and the `active` field.
- Allowed and denied access audit: recorded through the Audit Trail dependency.
- Dynamic behavior: Maker-Checker calls RBC; authorization limits are persisted rules, not banking-service conditionals.
